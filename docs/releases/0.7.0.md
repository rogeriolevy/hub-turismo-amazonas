# Candidata 0.7.0 — Hub Turismo Amazonas

**Registro atualizado:** 14/10/2026  
**Status:** verificada localmente; publicação na VPS e SMTP real pendentes.

## Foco

Acrescentar entrega opcional por e-mail aos avisos de reserva, preservando a caixa interna e as transações existentes.

## Escopo

- Pedidos e cancelamentos podem avisar gerente/equipe hoteleira ou operador; decisões podem avisar o turista.
- `BOOKING_EMAIL_NOTIFICATIONS=false` mantém o comportamento anterior. Para ativar, o ambiente precisa de SMTP válido e o worker Compose `booking-email-worker`.
- A tabela `booking_email_outbox` registra as entregas na mesma transação que cria a notificação interna.
- Um worker separado lê a fila com lease, respeita operações concorrentes no PostgreSQL, aplica espera exponencial a falhas e encerra uma entrega após oito tentativas; uma opção de linha de comando reabre entregas terminais somente com confirmação explícita.
- Mensagens incluem nome da empresa, referência curta e link interno. Notas da reserva e dados pessoais do hóspede não entram no corpo.
- O identificador da mensagem permanece estável nos retries. A entrega é ao menos uma vez: uma queda depois da aceitação pelo SMTP e antes da confirmação no banco pode repetir uma mensagem.
- A migration aditiva `020_booking_email_outbox.sql` não altera contas, reservas ou avisos existentes. A fila é estado transitório de entrega e fica fora da transferência SQLite→PostgreSQL; avisos internos continuam sendo transferidos.

## Verificação

- O teste SQLite usa um remetente simulado, valida destinatário e links, escape de HTML, idempotência, espera de retry, limite de oito tentativas e reabertura explícita; nenhuma mensagem real foi enviada.
- Em PostgreSQL 18.6 descartável, o teste de concorrência valida destinatários de equipe, consumo da fila, aviso ao turista após confirmação e o SQL de claim com `FOR UPDATE SKIP LOCKED`.
- `npm test`: 57 aprovados, 0 falhas e 3 ignorados por dependerem de POSIX/PostgreSQL; o teste de backup/restauração também passou em Node 22 Linux e os testes de transferência e concorrência passaram em PostgreSQL 18.6 descartável.
- `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm run check:architecture`, `npm run check:version` e `npm run check:vps-release` passaram. `npm run test:integration` passou contra a build de produção.
- A imagem Docker 0.7.0 foi construída. Em dois Compose descartáveis, PostgreSQL e web ficaram saudáveis, a migration 020 foi aplicada e o worker rodou como UID 1000 sem publicar porta, com e sem a flag de e-mail. O modo habilitado usou SMTP fictício e fila vazia; nenhuma mensagem foi enviada.
- A prévia do backup oficial passou em PostgreSQL 18.6 com a migration 020; preservou as contagens previstas, conferiu as imagens e reverteu a transação. O comparador somente leitura confirmou novamente origem e backup equivalentes: 24 tabelas, 5.480 linhas e fingerprint SHA-256 `893259276d3d3c085eea4f413cf013fb4e208c239f40206e00106e1f9fb71b1c`. A base oficial e o backup não foram alterados. Nenhum dado foi enviado à VPS.

## Configuração e retorno

O padrão continua desligado. Na VPS, configurar `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` e `SMTP_FROM`, então definir `BOOKING_EMAIL_NOTIFICATIONS=true`. O preflight valida a combinação. Os serviços `web` e `booking-email-worker` usam a mesma imagem; o worker não publica porta. Após corrigir uma falha persistente de SMTP, a administração pode reabrir entregas terminais pelo script operacional, com confirmação explícita.

A migration só acrescenta uma tabela, então a aplicação 0.6.2 continua compatível com o schema 0.7.0 se for necessário voltar o serviço web. Em um retorno, recriar também o worker com a versão anterior e desativar o canal até retomar uma versão que consuma a fila. A fila de entregas pode ser preservada sem afetar reservas ou notificações internas.
